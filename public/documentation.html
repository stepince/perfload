Installation & Setup

No installation required. PerfLoad is available as a pre-built Docker image — just run it.

Prerequisites

  • Docker installed and running

1. Start the container

docker run -d --name perfload \
  -p 3000:3000 \
  -v perfload-runs:/app/runs \
  perfload/perfload-runner:latest
  • -d — run in the background
  • -p 3000:3000 — dashboard, API & k6 live dashboard (all on one port)
  • -v perfload-runs:/app/runs — persist run history across restarts

To pin a specific release instead, replace latest with a version tag, e.g. 1.6.0.

2. Open the dashboard

InterfaceURL
Dashboardhttp://localhost:3000/
Workbenchhttp://localhost:3000/load-tester.html
k6 live dashboardhttp://localhost:3000/runs/<id>/dashboard/live/

Managing the container

# Stop
docker stop perfload

# Start again
docker start perfload

# View logs
docker logs perfload

Tip: Run history is stored in the perfload-runs Docker volume and is preserved when you stop, restart, or upgrade the container.

🚀 Getting Started

Turn any curl command into a load test in seconds.

1. Paste your curl

curl -X GET 'https://api.example.com/products'

2. Configure the test

  • Users → number of concurrent users
  • Duration → how long the test runs
  • Ramp-up → how quickly load increases

Tip: Start small (1–5 users) for real systems.

3. Run the test

Click Run Test to see:

  • Live results
  • Latency chart
  • Success / failure counts

4. Add variables (optional)

Use variables to change request values:

${variableName}

Example:

curl -X POST 'https://api.example.com/cart' \
  -H 'Content-Type: application/json' \
  -d '{"productId": "${productId}", "qty": 1}'

Define:

  • Name: productId
  • Type: Sequential
  • Values: 101, 102, 103

Each request will use the next value.

5. Compare runs

Select multiple runs and click Compare to analyze performance differences.

Variables

Variables allow dynamic values in your requests.

Syntax

${variableName}

Built-in Variables

VariableDescription
${random}Random number (0–999999)
${user}Virtual user ID
${iteration}Request number per user
${timestamp}Current timestamp
${isoTimestamp}ISO formatted time
${hostname}Hostname of the machine running the test

User Variables

Each variable has:

  • Name
  • Type
  • Values

Variable Types

Constant (same value every time)

Values: 101, 102, 103

Request 1 → 101
Request 2 → 101
Request 3 → 101

Sequential (next value per request)

Values: 101, 102, 103, 104

Request 1 → 101
Request 2 → 102
Request 3 → 103
Request 4 → 104
Request 5 → 101 (loops back)

Best for: realistic data simulation

Random (random value each request)

Values: 101, 102, 103

Request 1 → 102
Request 2 → 101
Request 3 → 103

Best for: spreading load, avoiding caching

Example

curl -X GET 'https://api.example.com/products?category=${category}'

Variable:

category
Type: Random
Values:
books
electronics
clothing

Each request hits a different category.

Run Single vs Run Test

  • Run Single: variables resolve once, using the first value
  • Run Test: variables resolve per virtual user and per iteration, just like a real load test

Key Idea

  • Constant → same value
  • Sequential → next value
  • Random → different value

Variables control how your data changes across requests.

Execution Modes

PerfLoad supports two ways to run a request, both executed by the PerfLoad runner (Docker / k6) rather than the browser:

  • Run Single
    Sends one request through the runner and shows the full response.
    • Best for debugging and validation
    • Shows full response body
    • No load — just a single request
  • Run Test
    Runs a full load test on the runner using k6, with multiple virtual users.
    • Simulates concurrent users
    • Shows live results and latency chart
    • Not limited by browser performance — can run inside a VPC or close to your backend

Tip: Use Run Single to verify your request, then Run Test for real load testing. Set the runner's URL once under Settings — it applies to every run, not per project.

CI/CD Integration

Uses only curl and jq — no Node.js required in your pipeline. Configure a test once in the UI, store the Run ID, then replay it on every deploy.

Setup

  1. Run a test in the Workbench and copy the Run ID from the dashboard
  2. Store it as a CI/CD environment variable (e.g. BASELINE_RUN_ID)
  3. Use the script below in your pipeline

Script

RUNNER=http://my-runner:3000

# 1. Fetch config from the baseline run, override VUs
CONFIG=$(curl -s $RUNNER/runs/$BASELINE_RUN_ID | jq '.config | .users = 50')

# 2. Start a new run
NEW_ID=$(curl -s -X POST $RUNNER/runs \
  -H "Content-Type: application/json" \
  -d "$CONFIG" | jq -r '.id')

echo "Run ID: $NEW_ID"

# 3. Poll until finished
while true; do
  STATUS=$(curl -s $RUNNER/runs/$NEW_ID/status | jq -r '.status')
  echo "Status: $STATUS"
  [ "$STATUS" = "finished" ] || [ "$STATUS" = "failed" ] || [ "$STATUS" = "stopped" ] && break
  sleep 2
done

# 4. Print results
curl -s $RUNNER/runs/$NEW_ID/summary | jq '{
  totalRequests: .metrics.http_reqs.values.count,
  rps:           .metrics.http_reqs.values.rate,
  latencyAvg:    .metrics.http_req_duration.values.avg,
  latencyP95:    .metrics.http_req_duration.values["p(95)"],
  latencyP99:    .metrics.http_req_duration.values["p(99)"],
  errorRate:     .metrics.http_req_failed.values.rate
}'

GitHub Actions example

jobs:
  load-test:
    runs-on: ubuntu-latest
    steps:
      - name: Run load test
        id: load_test
        run: |
          RUNNER=${{ vars.RUNNER_URL }}

          CONFIG=$(curl -s $RUNNER/runs/${{ vars.BASELINE_RUN_ID }} | jq '.config | .users = 50')
          NEW_ID=$(curl -s -X POST $RUNNER/runs \
            -H "Content-Type: application/json" \
            -d "$CONFIG" | jq -r '.id')

          while true; do
            STATUS=$(curl -s $RUNNER/runs/$NEW_ID/status | jq -r '.status')
            [ "$STATUS" = "finished" ] || [ "$STATUS" = "failed" ] || [ "$STATUS" = "stopped" ] && break
            sleep 2
          done

          SUMMARY=$(curl -s $RUNNER/runs/$NEW_ID/summary)
          echo "p95=$(echo $SUMMARY | jq '.metrics.http_req_duration.values["p(95)"]')" >> $GITHUB_OUTPUT
          echo "$SUMMARY" | jq '.metrics'

      - name: Show p95 latency
        run: echo "p95 latency = ${{ steps.load_test.outputs.p95 }} ms"

Override execution parameters

Use jq to override any config field before posting:

# Smoke test
CONFIG=$(curl -s $RUNNER/runs/$BASELINE_RUN_ID | jq '.config | .users = 5 | .duration = "30s"')

# Load test
CONFIG=$(curl -s $RUNNER/runs/$BASELINE_RUN_ID | jq '.config | .users = 100 | .duration = "5m"')

Tip: The runner persists run history across image updates using a Docker named volume, so your baseline Run ID stays valid after deployments.

AI Skills

Skills are markdown files that teach any AI assistant how to drive PerfLoad via its REST API. Instead of building LLM analysis into the app, skills keep the tool lightweight and model-agnostic — the AI reads the skill, then calls the API directly.

Getting the skills

  1. Open the workbench at /load-tester.html
  2. Click the Settings button in the top-right header
  3. Download the skill file(s) you need
  4. Load the downloaded .md file into your AI assistant as a skill

Skills are also served directly by the runner:

GET /skills/workbench.md
GET /skills/dashboard.md

Workbench skill

Covers the full workbench workflow: profile management, form field IDs, running load tests and single requests via the REST API, and reading results.

Example prompts:

  • "Create a profile named smoke-test targeting https://api.example.com with 10 users for 60 seconds"
  • "Run a load test with the current settings and report back the p95 latency and error rate"
  • "Increase users to 50 and re-run, then compare the results"

Dashboard skill

Covers the dashboard workflow: listing runs, reading metrics from the summary API, generating comparison PDF reports, and interpreting results.

Example prompts:

  • "Compare the last 3 finished runs and summarize the performance trend"
  • "Find any runs where the error rate exceeded 1% and report their names and timestamps"
  • "Generate a comparison PDF for runs named smoke-test"

Tip: The dashboard skill uses POST /runs/compare/report.pdf to generate multi-run comparison reports programmatically — no need to select runs in the UI.

⚠️ Safety: This tool generates load. Be careful when running against production systems.
